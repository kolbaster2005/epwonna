# EP WONNA — React-прототип

Образовательная платформа для подготовки к экзаменам EP (Австрия). Фронтенд:
главная страница, общий шаблон страницы экзамена (EPM / EPD / EPE), прохождение
теста, страница «О проекте» — и админ-панель для управления пробниками и
вопросами. Данные пробников/вопросов хранятся в Supabase (Postgres + Auth),
подключение — см. раздел «Supabase» ниже.

## Стек

- React 18
- React Router 6 (клиентский роутинг)
- Vite (сборка и dev-сервер)
- **Supabase** — Postgres (данные пробников/вопросов) + Auth (регистрация/вход)
- **SCSS** с архитектурой по слоям (см. ниже) — компилируется автоматически, ничего дополнительно настраивать не нужно, `sass` уже в devDependencies

### Меню

Пять разделов в шапке:
1. **Главная** — обычная ссылка.
2. **EP – экзамены** — группирующий пункт без своей страницы: наведение
   открывает список EPM / EPD / EPE, каждый ведёт на уже существующую
   страницу экзамена. Реализовано как `<span className="nav-link">`,
   а не `<Link>` — кликать некуда, так и задумано.
3. **Вступительные в вузы** — та же логика, список берётся из
   `data/universities.js`, ведёт на страницы-заглушки `UniversityPage`
   (`/uni/wu`, `/uni/uniwien`, `/uni/tuwien`).
4. **Моё обучение** (`/my-learning`) — обычная ссылка на страницу с
   виджетами, см. ниже.
5. **О проекте** — обычная ссылка.

«Админка» осталась отдельным пунктом после этих пяти (см. раздел
«Админка» ниже) — по брифу это не часть основного меню продукта, а
служебный раздел.

В мобильном меню группирующие пункты 2 и 3 отрисованы как обычный текст
(`.mnav-group-label`, не ссылка) с подсписком ссылок под ним — принцип
тот же, просто без наведения (на тач-устройствах его нет).

### «Моё обучение»

Раздел помечен баннером «в разработке» — ни авторизации, ни сохранения
результатов пока нет (см. `services/testsService.js` про мок-бэкенд).
Тем не менее по брифу там уже должны быть виджеты, поэтому они на месте
и работают на данных из `data/myLearningMock.js`:
- **Прогресс по предметам** — для каждого EPM/EPD/EPE: сколько пробников
  пройдено из общего числа (полоса прогресса) и **среднее время на
  пробник** — то самое, что просили показывать в виджете;
- **Последние пробники** — список последних попыток с результатом в % и
  датой;
- **Динамика результатов** — график результата по попыткам во времени.
  Библиотек для графиков в проекте нет (не хотелось тянуть зависимость
  ради одного график), поэтому это простой самодельный SVG line-chart
  прямо в `MyLearning.jsx`.

Когда появятся аккаунты и таблица попыток прохождения в Supabase,
`myLearningMock.js` заменяется на сервис по той же схеме, что и
`seedTests.js` → `testsService.js`.

Страницы `/epm`, `/epd`, `/epe` рендерятся одним и тем же компонентом
`ExamPage`, которому передаётся `examKey` — так что структура страниц
гарантированно одинаковая, а различия (цвет, тексты, список пробников)
берутся из `examData.js` и `testsService.js`.

Клик по карточке пробника ведёт не на модалку, а на отдельную страницу
`/:examKey/probnik/:testId` (`TestDetailPage`) — хлебные крошки, иконка,
список метаданных (кол-во заданий/время/официальный статус/год) слева и
описание с кнопкой «Начать» справа. Кнопка «Начать» уже запускает сам тест.

Прохождение конкретного пробника — маршрут `/:examKey/test/:testId`
(например `/epm/test/epm-2026-10`), рендерится компонентом `TestPage`,
общим для всех трёх экзаменов по той же логике. Дизайн левой панели и
общий вид страницы сверены с референс-скриншотом заказчика (в своей
цветовой палитре): компактная шапка «Вопросы» с таймером и паузой в одну
строку, тонкая полоса прогресса «Отвечено X из Y», номера вопросов
сгруппированы по категориям (5 в ряд), легенда — не закрашенные точки, а
контурные квадраты. Справа — бейдж-пилюля «Вопрос N из M», серые
uppercase-подписи «ВОПРОС» / «ВАРИАНТЫ ОТВЕТОВ», сами варианты — плоские
строки с разделителями (не карточки), кнопки «Назад» / «Пропустить» /
«Ответить» / «Далее».

Группировка по категориям (`question.category` в `seedTests.js`) — часть
общего ТЗ на админку (см. ниже): для EPM это «Часть А» / «Часть Б», для
письменной части EPD/EPE — «Чтение» / «Грамматика» / «Письмо». Группы
строятся автоматически из данных вопросов (`groupByCategory` в
`TestPage.jsx`), без отдельного конфига.

### Типы вопросов

Вопрос — это не всегда «варианты ответа». Вся логика проверки и рендеринга
инпутов вынесена в `src/utils/grading.js` (проверка) и
`src/components/QuestionAnswerInput.jsx` (UI), заведённые на поле
`question.type`:

| `type` | Кто использует | Что вводит человек | Как проверяется |
|---|---|---|---|
| `multiple_choice` | Все предметы | Чекбоксы (можно несколько) | Точное совпадение с `correctOptionIds` → верно/частично/неверно |
| `numeric` | Математика | Число | `\|введено − correctValue\| ≤ tolerance` (по умолчанию ±0.1) |
| `true_false` | Чтение (EPD/EPE) | Верно/Неверно по каждому утверждению | Доля угаданных утверждений → верно/частично/неверно |
| `heading_match` | Чтение (EPD/EPE) | Строка вида «A, C, B, D» | Посимвольное сравнение с `correctSequence` |
| `short_answer` | Чтение/грамматика (EPD/EPE) | Короткое слово/фраза | Точное совпадение (без учёта регистра/пробелов) с одним из `acceptedAnswers` |
| `free_text` | Письмо (EPD/EPE) | Свободный текст | Никогда — вердикт всегда `'ungraded'` |
| `multi_part` | Математика (реальные многосоставные задачи) | Общий текст условия + несколько независимо проверяемых пунктов (`parts`) | Каждый пункт — по своим правилам, итог по вопросу — доля верных пунктов → верно/частично/неверно |

Ни `TestPage.jsx`, ни `AdminTestEditor.jsx` не знают деталей конкретного
типа за пределами `grading.js`/`QuestionAnswerInput.jsx`: страница теста
просто рендерит `<QuestionAnswerInput question={...} .../>` и красит по
verdict'у из `getVerdict()`. Добавить новый тип — это добавить один
`case` в оба файла, не переписывать существующие.

Числовые вопросы по математике заведены с допуском ±0.1 — см.
`epm-demo-1-q2` в `supabase/seed.sql`. True/False и подбор заголовков —
демо-вопросы в категории «Чтение» у EPD/EPE, `free_text` — демо-вопрос в
категории «Письмо». Конкретные форматы письменных заданий (пост в блог
для английского, реальные немецкие форматы) пока не заведены — ждут
материалов от заказчика.

#### `multi_part` — составные вопросы с несколькими пунктами

Реальные экзаменационные задания часто выглядят не как «один вопрос —
один ответ», а как общий текст условия и несколько пунктов (a, b, b.i,
b.ii...), каждый со своим типом ответа и своей проверкой — например
«заполните таблицу» + «посчитайте 4 вероятности». Под это заведён
`multi_part`: у вопроса есть `parts: [{ id, label, type, ... }]`, каждая
часть — это, по сути, мини-вопрос (сейчас поддержаны `numeric` и
`table`), проверяется независимо, но всё оформлено на одной карточке в
навигаторе — ровно так, как в реальном пробнике. Итоговый вердикт по
всему вопросу — верно, если верны все части; неверно — если ни одна; иначе
частично.

`table` — это не отдельный `type` вопроса, а тип части внутри
`multi_part`: сетка `columns` × `rows`, у каждой ячейки либо `{ given }`
(показывается как текст, не редактируется — то, что дано в условии
напрямую), либо `{ correctValue, tolerance? }` (пустая ячейка, которую
заполняет человек). Живой пример — демо-вопрос `epm-demo-1-q3` в
`supabase/seed.sql`, это тот самый пример с фото, который вы прислали
(фирма закупает микрочипы у двух поставщиков): таблица с частично
заданными, частично вычисляемыми ячейками + 4 отдельных процентных
вопроса под ней — всё внутри одной карточки на странице теста.

`multi_part` можно завести и через саму админ-панель — выберите «Составной
вопрос» в «Тип ответа», дальше кнопками добавляются пункты («Числовой
пункт» / «Пункт-таблица»), у пункта-таблицы отдельно управляются строки и
колонки, а по каждой ячейке — переключатель «Дано» (фиксированное
значение из условия, показывается как текст) / «Вычисляется» (пустая
ячейка + правильный ответ и допустимая погрешность для неё). Всё то же
самое, что и в живом демо-вопросе `epm-demo-1-q3` в `supabase/seed.sql` —
просто теперь можно собрать такой вопрос руками, не трогая SQL.

Количество правильных ответов у вопроса заранее не известно пользователю
и нигде не хранится отдельным флагом «один/несколько» — все варианты
показаны чекбоксами, отметить можно сколько угодно, а факт «один правильный
ответ или несколько» вычисляется на лету из `correctOptionIds.length`
только когда это нужно для проверки (чтобы интерфейс сам не выдавал это
раньше времени).

Цикл ответа на вопрос — два состояния:
1. **До отправки.** Человек свободно редактирует ответ (в любом из пяти
   форматов выше), никакой подсветки правильности нет, кнопка называется
   «Ответить» (задизейблена, пока `hasAnswer()` не видит валидного ввода).
2. **После отправки.** Клик по «Ответить» фиксирует ответ — изменить его
   больше нельзя — и показывает результат: **зелёным** — верно,
   **оранжевым** — частично верно, **красным** — неверно, **синим** —
   ответ сохранён, но тип вопроса не проверяется автоматически
   (`free_text`). Кнопка меняется на «Далее» (на последнем вопросе — на
   «Завершить тест»).

Этот же набор состояний красит номера вопросов в навигаторе слева
(добавлен четвёртый, синий статус — «без автопроверки»), а в конце теста
результат раскладывается на «верно / частично верно / неверно / не
проверяется автоматически / без ответа», а не просто на общий счёт.

Кнопка «Завершить тест» (и в сайдбаре, и на последнем вопросе, после
«Ответить») сначала проверяет, остались ли вопросы, на которые ответ ещё
не был отправлен, и если да — переспрашивает через `confirm`,
действительно ли человек хочет закончить.

### Устная часть

Маршрут `/:examKey/oral/:testId` (`OralTestPage.jsx`), для EPD и EPE —
у EPM устной части нет. Контент лежит в `test.oralTask.stages` в
`seedTests.js`, а не в `test.questions` — это принципиально другой формат
(карточки/фото + таймер подготовки, а не квиз), поэтому у него отдельная
страница и отдельная модель данных:

- **EPD** — два этапа: (1) выбор одной из двух карточек (цитата или
  график) с 20 минутами на подготовку монолога; (2) фотография для
  спонтанного диалога, без отдельного времени на подготовку (как в ТЗ).
- **EPE** — один этап: две фотографии для сравнения, 20 минут на
  подготовку, затем — ответ с вопросами экзаменатора.

Каждый этап проходит через состояния «выбор карточки» (если применимо) →
«подготовка» (таймер с паузой и кнопкой «Пропустить подготовку») →
«представление ответа» (кнопка «Далее»/«Завершить устную часть»). Внизу
страницы — постоянный дисклеймер, текст из ТЗ дословно: «Функция
автоматической проверки будет доступна позже. В данный момент проект
находится на этапе запуска.» Реальных фото/графиков нет — вместо `<img>`
показывается плейсхолдер-карточка (`components/Icons.jsx` → `IconImage`);
загрузка настоящих фото через админку, как и сам конструктор этапов
устной части, — следующий шаг (см. ниже).

### Письменная / устная часть — переключатель

И на `/epd`, `/epe`, и в самой админке (`/admin/epd`, `/admin/epe`) под
вкладками «Пробники»/«Об экзамене» (в админке — прямо под заголовком)
есть переключатель «Письменная часть / Устная часть»
(`exam.phases` в `examData.js`; у EPM его нет — там `exam.phases`
не задан, и переключатель просто не рендерится). Публичная страница
фильтрует пробники по `test.format`, годы в фильтре «Год» пересчитываются
только по пробникам активной фазы. Кнопка «+ Добавить пробник» в админке
передаёт выбранную фазу в форму создания через `?format=`, так что новый
пробник сразу создаётся в нужной части.

Фильтр «Формат» из общей панели фильтров убрал — он дублировал
переключатель фаз, а два контрола с одним и тем же смыслом только путают.

### Полное ТЗ на админку — что сделано, что дальше

Заказчик прислал развёрнутое ТЗ на интеграцию с Supabase, структуру
админки и (отдельным дополнением) — разные типы ответов с проверкой и
формат устной части. Реализовано:
- редизайн страницы прохождения теста, включая `question.category`
  (группировка в сайдбаре);
- переключатель письменная/устная часть — на публичных страницах и в
  админке;
- пять типов вопросов (`multiple_choice`/`numeric`/`true_false`/
  `heading_match`/`free_text`) с проверкой и полями под каждый тип уже
  в самой админке, не только в данных;
- интерфейс устной части (карточки/фото, таймер подготовки, дисклеймер)
  для EPD и EPE.

- переключатель письменная/устная часть — на публичных страницах и в
  админке, теперь расположен под панелью фильтров;
- пять типов вопросов (`multiple_choice`/`numeric`/`true_false`/
  `heading_match`/`free_text`) с проверкой и полями под каждый тип уже
  в самой админке, не только в данных;
- интерфейс устной части (карточки/фото, таймер подготовки, дисклеймер)
  для EPD и EPE, с демо-пробниками в `supabase/seed.sql`;
- **категория вопроса теперь настраивается прямо в админке** — выпадающий
  список «Категория» в редакторе вопроса, варианты берутся из
  `exam.categories` в `examData.js` (свои для каждого экзамена: «Часть
  А»/«Часть Б» у EPM, «Чтение»/«Грамматика»/«Письмо» у EPD/EPE). Раньше
  это можно было поменять только прямой правкой SQL — теперь понятно,
  откуда берётся группировка в сайдбаре на странице теста.

Осталось по списку из ТЗ:
- конструктор устной части в админке — сейчас `oral_task` заводится
  только через SQL (`supabase/seed.sql`), а фото/карточки — не настоящие
  изображения, а плейсхолдеры;
- реальные форматы письменных заданий по языкам (пост в блог для
  английского, немецкие форматы) — ждут материалов от заказчика;
- учёт того, что категорий/предметов станет больше трёх — архитектура уже
  это допускает (`examList`/`exams` нигде не хардкодят число экзаменов за
  пределами `examData.js`), но сам процесс добавления нового предмета
  через админку ещё не продуман.

### Вкладка «Об экзамене»

`exam.about` в `examData.js` — не плоский список «заголовок + один абзац»,
а массив секций с типизированными блоками контента и опциональными
вложенными подразделами **любой глубины** (рендерит
`components/AboutSection.jsx`, рекурсивно: h3 → h4 → h5 → h6):

```js
{
  h: 'Как проходит экзамен',              // заголовок секции (h3)
  content: [
    { type: 'p', text: '...' },            // абзац
    { type: 'list', items: [...] },        // список; ordered:true → <ol>
    { type: 'note', text: 'Важно: ...' },  // выделенная плашка-предупреждение
  ],
  sub: [                                    // вложенные подразделы (h4)
    {
      h: 'Письменная часть',
      content: [...],
      sub: [                                 // у подраздела тоже может быть sub (h5) —
        { h: 'Чтение', content: [...] },     // так устроена EPD: письменная часть →
        { h: 'Аудирование', content: [...] },// блоки (h4) → каждый блок (h5)
      ],
    },
    { h: 'Устная часть', content: [...] },
  ],
}
```

Элемент списка — либо просто строка, либо `{ lead, text, url? }`, где
`lead` рендерится жирным («**Формат:** экзамен состоит из...»), а если
задан `url` — ещё и ссылкой (см. «Полезные материалы и ссылки»: пока
ведут на `#`-заглушку, заменить на реальные адреса, когда появятся).
Заполнено по материалам заказчика для всех трёх экзаменов — EPM, EPD и
EPE. Места вида `___` (не указанные проходные баллы и т.п.) оставлены
как есть в исходном материале — их значения ещё предстоит уточнить.

### Фильтры и поиск на странице «Пробники»

Набор фильтров у каждого экзамена свой и полностью описывается конфигом
`exam.filters` в `examData.js` — компонент `TestFilters.jsx` ничего не
знает про конкретные поля, он просто рендерит один `<select>` на каждую
запись конфига (с иконкой, подобранной по имени поля) и матчит
`test[field] === выбранное_значение`, плюс текстовый поиск по названию.
Добавить/убрать фильтр — это правка данных, а не кода:
- **EPM**: тип пробника (официальный/неофициальный), тема (алгебра,
  геометрия, функции, статистика и векторы), год;
- **EPD / EPE**: формат (письменный/устный), тема (питание, окружающий
  мир, экономика), год.

Список тем берётся из `exam.topics`, список годов — вычисляется на лету
из загруженных пробников (чтобы не рассинхронизироваться с данными). В
реальной БД это будут `SELECT DISTINCT year` и таблица `topics`
соответственно.

Карточка пробника (и страница деталей) показывает три бейджа с иконками —
количество вопросов, время на прохождение и официальный/неофициальный
статус — вместо прежних статичных «Тест» / «С решениями».

### Иконки и цвет экзамена

`components/Icons.jsx` — общий набор простых inline-SVG-иконок
(список/часы/щит/календарь/поиск/дом/шеврон), используется в фильтрах,
на карточках и в хлебных крошках. `components/ExamIcon.jsx` — иконка
конкретного экзамена (математика/языки), принимает `color` — можно
поставить белым на сплошном цветном кружке (главная страница) или
акцентным цветом на светлом кружке (карточки пробников, страница
деталей). Оба компонента переиспользуются везде, где нужна иконка —
дублировать SVG по компонентам больше не нужно.

### Слой данных: теперь настоящий Supabase, не мок

Раньше `testsService.js` был просто переменной в памяти. **Это больше не
так** — с этого шага он делает настоящие запросы к Supabase
(`supabase.from('tests').select(...)` и т.д.), см. подробную
инструкцию по подключению в разделе «Supabase» ниже. Важно, что при этом
изменился **только один файл**: `ExamPage`, `TestDetailPage`, `TestPage`,
вся админка как писали `await listTests(examKey)` / `await getTest(...)`,
так и продолжают — сигнатуры функций и форма возвращаемых данных не
поменялись ни на бит. Это не случайность, а ровно то, ради чего с самого
начала все страницы ходили через сервис-слой, а не читали данные напрямую.

Разделение по файлам такое:
- `examData.js` — то, что админ **не** редактирует через эту панель:
  цвета, названия экзаменов, список тем, конфиг фильтров, текст «Об
  экзамене». Остаётся синхронным импортом, роутить через сервис-слой
  незачем.
- `supabase/schema.sql` + `supabase/seed.sql` + `testsService.js` — то,
  что редактируется: сами пробники и вопросы. Живут в базе, а не в коде.

Внутри `testsService.js` есть небольшой слой преобразования: колонки в
Postgres — snake_case (`short_description`, `is_official`,
`correct_option_ids`), а формат данных в приложении — camelCase
(`shortDescription`, `isOfficial`, `correctOptionIds`). Функции
`rowToTest`/`rowToQuestion`/`testToRow`/`questionToRow` — единственное
место, где происходит это преобразование; остальной код о нём не знает.

Каждое поле теста 1:1 соответствует колонке таблицы `tests`
(`supabase/schema.sql`). Количество вопросов на карточке **не хранится
отдельным числом** — считается на лету как `test.questions.length`, чтобы
не могло разъехаться с реальным списком вопросов.

## Supabase

Проект подключается к вашему собственному проекту Supabase — я не могу
создать его за вас (у меня нет доступа к supabase.com и нет ваших
ключей), но весь код уже готов, осталось только это разовое
подключение.

### 1. Создать проект и получить ключи

1. Зайдите на [supabase.com](https://supabase.com), создайте новый проект
   (бесплатного тарифа достаточно).
2. В настройках проекта: **Project Settings → API** — скопируйте
   **Project URL** и **anon public key**.
3. В корне проекта скопируйте `.env.example` в `.env` и вставьте туда эти
   два значения:
   ```
   VITE_SUPABASE_URL=https://ваш-проект.supabase.co
   VITE_SUPABASE_ANON_KEY=ваш-anon-ключ
   ```
   `.env` уже в `.gitignore` — реальные ключи в репозиторий не попадут.

### 2. Создать таблицы и загрузить тестовые данные

В Supabase Dashboard откройте **SQL Editor → New query** и по очереди
выполните два файла из папки `supabase/` этого проекта:

1. `supabase/schema.sql` — создаёт три таблицы (`profiles`, `tests`,
   `questions`), включает Row Level Security и настраивает права: читать
   пробники может кто угодно, редактировать — только пользователи с
   ролью `admin`.
2. `supabase/seed.sql` — добавляет **по одному демо-пробнику на каждый
   раздел** (EPM/EPD/EPE), как вы и просили — просто чтобы проверить, что
   всё подключено и работает. Их можно свободно удалить через
   `/admin/<раздел>` и завести настоящие.

Оба файла безопасно перезапускать — используют `if not exists` /
`on conflict do nothing`.

> Если вы уже создавали таблицу под старым именем `mock_tests` (в самой
> первой версии `schema.sql`) — не пересоздавайте всё заново, просто
> выполните `supabase/migrate_rename_mock_tests.sql`. Она переименовывает
> таблицу на месте, без потери данных: строки, индексы, политики RLS и
> внешний ключ из `questions` — всё это привязано к таблице внутри
> Postgres не по имени, а автоматически следует за переименованием.

### 3. Сделать себя админом

Права на запись в `tests`/`questions` (создание/редактирование/
удаление пробников через `/admin`) есть только у пользователей с ролью
`admin` — это защита на уровне самой базы (RLS), а не только на уровне
интерфейса. Чтобы админка реально заработала:

1. Зарегистрируйтесь в самом приложении (кнопка «Войти» → «Зарегистрироваться»).
2. Подтвердите почту по ссылке из письма (Supabase Auth по умолчанию
   требует подтверждения — это можно отключить в **Authentication →
   Providers → Email**, если мешает при разработке).
3. В SQL Editor выполните (с вашим email):
   ```sql
   update public.profiles set role = 'admin' where email = 'вы@example.com';
   ```

После этого сохранение/удаление пробников в `/admin` будет проходить —
без роли `admin` запросы на запись будут молча отклоняться политикой RLS
(вернётся ошибка, которую покажет форма).

### 4. Запустить

```bash
npm install
npm run dev
```

Если что-то не подключилось — при пустых переменных окружения в консоли
браузера появится явное сообщение об этом (`src/lib/supabaseClient.js`),
а не белый экран или тихо зависшая загрузка.

### Авторизация

Кнопка «Войти» в шапке (и в мобильном меню) открывает модалку
(`components/AuthModal.jsx`) с переключением «Вход / Регистрация» —
обычный email + пароль через `supabase.auth`. Состояние сессии живёт в
`contexts/AuthContext.jsx` (`useAuth()`), которым обёрнуто всё приложение
в `main.jsx`; после входа кнопка «Войти» заменяется на email пользователя
и «Выйти».

Регистрация сразу создаёт запись в `profiles` (через триггер в
`schema.sql`) с ролью `user` по умолчанию — админом делает только прямой
`update` в SQL Editor, как в шаге 3 выше. Сохранение прогресса
прохождения пробников по пользователю — следующий шаг, сейчас реализован
только сам факт входа/регистрации/выхода, как и просили.

### Выбор аватара

Клик по кружку в шапке открывает под email сетку из 10 квадратиков: первый —
«без фото» (серый, перечёркнутый кружок), остальные девять — сами аватары.
Клик по любому — сразу подставляет его в кружок и сохраняет выбор.

Сами картинки — **не в БД**. Это фиксированный набор файлов проекта
(`src/assets/avatars/avatar-1.jpg` … `avatar-9.jpg`, подключены через
`src/data/avatars.js`), собираются Vite'ом как обычные ассеты. В базе
(`profiles.avatar_key`, добавлено в `supabase/schema.sql`) хранится только
маленькая текстовая метка — какой именно вариант выбран (`'avatar-3'` или
`null` для «без фото»), а не сам файл.

Сейчас там 9 сгенерированных цветных заглушек в фирменной палитре —
у вас ещё нет реальных фото. Чтобы подставить настоящие: положите файлы в
`src/assets/avatars/`, поменяйте пути импорта в `avatarOptions` в
`src/data/avatars.js` — больше нигде ничего менять не нужно, ни сетка
выбора, ни кружок в шапке, ни колонка в БД не завязаны на конкретный файл,
только на `id`.

Заодно, раз через выбор аватара приложение теперь реально может писать в
`profiles` от имени пользователя, в `schema.sql` добавлен триггер
`prevent_self_role_change` — он тихо не даёт обновлению поменять
`role`, если запрос пришёл не от вас напрямую из SQL Editor (там
подключение идёт от суперпользователя `postgres`, а не от обычного
клиента). Без этого политика RLS «обновлять можно свою же строку» заодно
разрешила бы пользователю проставить себе `role = 'admin'` через тот же
запрос.

### Админка

Пункт «Админка» в шапке (и в мобильном меню) виден **только** пользователям
с ролью `admin` — так же, как и сам переход на `/admin/*`: все эти роуты
обёрнуты в `RequireAdmin` (`components/RequireAdmin.jsx`), который читает
`profile.role` из `AuthContext` и редиректит на главную любого, кто не
залогинен или залогинен без роли `admin`. Пока сессия/профиль ещё
загружаются, вместо редиректа коротко показывается «Загрузка…», чтобы не
дёрнуть человека на главную раньше, чем станет известна его роль.

Это защита на уровне интерфейса — не единственная и не самая важная.
Настоящая граница — политики RLS в `supabase/schema.sql`: запросы на
запись в `tests`/`questions` в принципе отклоняются базой данных для
всех, кроме `admin`, независимо от того, что делает фронтенд. `RequireAdmin`
просто не даёт обычному пользователю даже увидеть форму, которая всё равно
не сохранилась бы.

Как назначить роль `admin` — см. «Supabase» → шаг 3 выше: это всегда
ручная правка через SQL Editor, из приложения самому себе роль поднять
нельзя (и не должно быть можно) — все, кто регистрируется, получают
`role = 'user'` по умолчанию через триггер `handle_new_user`.

Структура:
- **`/admin`** (`AdminHome`) — выбор раздела: EPM / EPD / EPE.
- **`/admin/:examKey`** (`AdminExamTests`) — таблица пробников экзамена:
  название, кол-во вопросов (то же вычисляемое значение, что и на
  публичной карточке), минуты, тип, тема, год; кнопки «Редактировать» и
  удаление (с подтверждением).
- **`/admin/:examKey/new`** и **`/admin/:examKey/:testId`**
  (`AdminTestEditor`) — форма пробника и вопросов на одной странице:
  - название, краткое описание (для карточки) и полное описание (для
    страницы пробника) — разделены на два разных поля;
  - минуты на прохождение, тип (официальный/неофициальный), тема (из
    `exam.topics`), формат (только у EPD/EPE — поле показывается
    автоматически, если у экзамена в `filters` есть `format`), год;
  - редактор вопросов: текст вопроса, необязательное пояснение (мелкий
    серый текст под вопросом на странице теста), необязательное фото
    (выбор файла — читается в `data:` URI через `FileReader`, без
    реального аплоада; когда появится Supabase Storage, это будет
    заменено на настоящую загрузку и URL) и варианты ответа с чекбоксами
    «правильный» — отметить можно сколько угодно вариантов, тип вопроса
    (один ответ / несколько) вычисляется из этого автоматически, а не
    задаётся отдельным переключателем;
  - PDF пробника (необязательно) — тем же способом через `FileReader`.
    Если PDF прикреплён, на странице пробника под заголовком появляется
    ссылка «Скачать пробник в PDF». **Важно:** сам файл в БД не хранится —
    в реальном проекте это `tests.pdf_url`, ссылка на объект в
    Supabase Storage; здесь эту ссылку временно изображает `data:` URI —
    Postgres хранит её как обычный текст, так что это уже работает и до
    подключения Storage, просто менее эффективно на больших файлах.

Загрузка фото и рендер и именованных демо-картинок (как треугольник в
одном из вопросов EPM), и настоящих `data:`/`http(s)` URL обрабатывает
один и тот же компонент — `components/QuestionImage.jsx`.

## SCSS-архитектура

Стили организованы по слоям (по мотивам ITCSS — от низкой специфичности к
высокой), каждый файл отвечает за одну вещь:

```
src/styles/
  abstracts/         Ничего не рендерят сами по себе — только токены и инструменты
    _variables.scss    цвета, отступы, breakpoints, радиусы, тени, z-index
    _mixins.scss       mq() для медиа-запросов, container(), button-reset() и т.д.
    _index.scss        "бочка" — форвардит variables + mixins одним @use

  base/               Сброс стилей и голые HTML-теги
    _reset.scss

  layout/             Крупные структурные части страницы
    _container.scss    .main-wrapper — общий контейнер продукта
    _header.scss        шапка, меню, дропдауны, мобильное меню
    _footer.scss

  components/         Переиспользуемые UI-блоки
    _buttons.scss
    _cards.scss         карточки направлений на главной + карточки пробников
    _tabs.scss           вкладки "Пробники" / "Об экзамене"
    _features-bar.scss
    _filters.scss        плашка фильтров + поиск на странице пробников

  pages/              Стили, специфичные для одной страницы
    _home.scss           hero-блок и иллюстрация
    _exam.scss           шапка страницы экзамена, текстовый блок "Об экзамене"
    _about.scss
    _test.scss            прохождение теста: навигатор, таймер, вопрос
    _oral.scss             устная часть: выбор карточки, таймер подготовки
    _test-detail.scss     хлебные крошки + карточка пробника перед стартом
    _admin.scss           админка: таблица пробников, форма, редактор вопросов
    _my-learning.scss     виджеты "Моё обучение" (прогресс, история, график)

  main.scss           Точка входа — просто список @use в нужном порядке
```

**Единый контейнер — `.main-wrapper`.** Он определён один раз через миксин
`container()` в `abstracts/_mixins.scss` и подключается в
`layout/_container.scss`. Класс применяется в трёх местах — этого достаточно,
чтобы накрыть всё приложение:
- на `<header className="main-wrapper site-header">` — контейнер и стиль шапки
  на одном элементе (учтите: это ограничивает саму плашку шапки шириной
  1220px по центру, а не тянет её на всю ширину экрана — так сделано сейчас
  сознательно, поменяйте на обёртку внутри `<header>`, если понадобится
  full-bleed шапка);
- на `<main className="main-wrapper">` в `App.jsx` — оборачивает контент
  всех страниц разом, поэтому внутри `Home.jsx` / `ExamPage.jsx` / `About.jsx`
  свои обёртки с `main-wrapper` больше не нужны;
- на `<div className="main-wrapper">` в `Footer.jsx` — футер физически вне
  `<main>`, поэтому ему нужна собственная обёртка.

Больше нигде в проекте не должно быть своих `max-width` / `padding-inline`
для контейнера — если нужно поменять поведение (например, добавить ещё один
breakpoint), меняем миксин `container()`, и это применяется сразу везде.

Отступы `.main-wrapper` по брейкпоинтам:
| Экран | Ширина от | Паддинг по бокам |
|---|---|---|
| Мобильный | 0 | 20px |
| Планшет | 768px (`$bp-md`) | 30px |
| Десктоп | 1220px (`$bp-xl`) | 60px |

Максимальная ширина контейнера всегда `1220px` (`$container-max-width`),
контент центрируется через `margin-inline: auto`.

**Как добавлять новое:**
- новый цвет/отступ/breakpoint → `abstracts/_variables.scss`;
- новый переиспользуемый миксин/функция → `abstracts/_mixins.scss`;
- новый общий UI-компонент (бейдж, инпут, тултип) → `components/_<имя>.scss`;
- что-то нужно только одной странице → `pages/_<имя-страницы>.scss`;
- в конце добавить одну строку `@use` в `main.scss` в соответствующий раздел.

Все партиалы, кроме `abstracts`, подключают токены и миксины одной строкой:
```scss
@use '../abstracts' as *;
```
После этого доступны все переменные (`$color-blue`, `$space-4`, …) и миксины
(`@include mq(md) { … }`, `@include container;`, `@include button-reset;`)
без префиксов.

## Запуск локально

Нужен установленный Node.js (18+) и подключённый проект Supabase — см.
раздел «Supabase» выше (создать проект, выполнить `schema.sql` и

```bash
cp .env.example .env   # затем вставьте туда свои ключи Supabase
npm install

```

Откроется адрес вида `http://localhost:5173`.

## Деплой на GitHub Pages

Репозиторий называется `epwonna`, значит сайт будет на
`https://<ваш-username>.github.io/epwonna/`. `vite.config.js`
(`base: '/epwonna/'`) и `public/404.html` (`segmentCount = 1`) уже
настроены под этот адрес — ничего менять не нужно, если название
репозитория не поменяется.

1. Создайте репозиторий `epwonna` на GitHub и запушьте в него этот проект.
2. Установите пакет для деплоя (уже есть в devDependencies) и выполните:
   ```bash
   npm run deploy
   ```
   Эта команда соберёт проект и запушит папку `dist` в ветку `gh-pages`.
3. В настройках репозитория на GitHub: **Settings → Pages → Source** выберите
   ветку `gh-pages`.
4. Через пару минут сайт будет на `https://<ваш-username>.github.io/epwonna/`.

**Если позже подключите свой домен** (упоминалось, что не сейчас, но
на будущее): поменяйте `base: '/'` в `vite.config.js`, `segmentCount = 0`
в `public/404.html`, добавьте файл `public/CNAME` с вашим доменом внутри,
и настройте DNS согласно инструкции GitHub (Settings → Pages → Custom domain).

### Про клиентский роутинг на GitHub Pages

GitHub Pages — статический хостинг и по умолчанию не умеет отдавать
`index.html` на прямые ссылки вида `/epm/about` (будет 404). В проекте уже
встроен стандартный обходной путь: `public/404.html` перенаправляет на
`index.html` с сохранением исходного пути, а скрипт в `index.html`
восстанавливает URL. Ничего дополнительно настраивать не нужно.
